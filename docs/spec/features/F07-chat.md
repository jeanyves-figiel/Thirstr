# F-07 Chat

## Purpose
Fast, private 1:1 and group messaging (party guest chats). E2EE, stored on device.

## Rules
- R-07.1 Protocol: MLS (RFC 9420) via OpenMLS. 1:1 = 2-member group (+ each side's devices). Party/activity chats = group (max 50).
- R-07.2 Starting a chat requires sender verified (F-03) unless replying to an inbound message.
- R-07.3 First message from a new contact: text only, max 500 chars, **no links/handles/phone/email** (client blocks + server rate signals). Links allowed once the other side replied.
- R-07.4 Message types: `text`, `media` (F-08), `album.grant`, `album.revoke`, `location.share` (TTL), `profile.private` (F-06 R-06.6), `link.preview` (I-01), `quick_reply`, `party.invite`, `checkin.started` (system), `vcheck` (video check, F-18 R-18.8–R-18.16, #159), `reaction`.
- R-07.5 Quick replies: "Yes 🔥", "Not now", "Later?", "Pics?", "Host?", "Can travel" + 3 custom (Settings).
- R-07.6 Disappearing messages: per chat 24 h / 7 d (default) / never; timer starts on read; both sides see setting; change creates a system message.
- R-07.7 Read receipts + typing: symmetrical; off for user → they don't see others'. Details: R-07.23.
- R-07.8 Inbox: sections "New" (unreplied inbound), "Chats", "Parties & groups"; sort by last activity; star, mute, archive, delete (local + leave group).
- R-07.9 Chat header: avatar, name, verified, distance bucket, Now status; actions: video call (Later), profile, ⋯ (block, report, disappearing timer, share location, start check-in). 1:1 ⋯ opens the shared safety sheet S-21 (F-15 R-15.17, #111): View profile, Date check-in, Hide / Block / Report tiles, then chat settings. Inbox long-press on a 1:1 chat: same tiles + Star, Mute, Archive, Delete.
- R-07.10 Unsolicited explicit media from someone you haven't replied to → blurred per Settings (blur/allow/block).
- R-07.11 Franking: each message carries commitment; report sends plaintext + opening to moderation (F-15).
- R-07.12 Delivery: online → realtime `message.new`; offline → content-free push; server deletes ciphertext on ack from all devices or after 30 d.
- R-07.13 Multi-device: all devices in user's MLS leaf set; new device added only via F-01 R-01.6.
- R-07.14 Offline compose: queued, sent on reconnect; optimistic UI. Details: R-07.17–R-07.19.
- R-07.15 Taps: separate "Taps" row at top of inbox; tap back = mutual → suggests "Say hi".

## Delivery, integrity and bad networks
- R-07.16 Sender states, shown under own messages: **Sending** (in outbox) → **Sent** (server stored it for every recipient device) → **Delivered** (≥ 1 recipient device decrypted it; E2EE `delivered` payload `{t: 'delivered', upTo}`) → **Read** (`read` payload). **Not sent · Retry** only when the outbox gives up (R-07.17) or the server returns the recipient as `undelivered`. Delivered/Read follow R-07.23; with receipts off the sender stops at Sent.
- R-07.17 Outbox: every outgoing payload (text, media, reaction, read/delivered receipt, disappearing, album, profile.private) is written to an encrypted on-device `outbox` **before** any network call, so it survives app kill, reboot and sign-in refresh. Drained FIFO per conversation (one chat never blocks another). Retry with exponential backoff 1 s, 2 s, 4 s … capped at 60 s, ± 20 % jitter; socket (re)connect, app launch, app foreground and push mean the network is back, so they drain at once without waiting out the backoff. A new message waits behind older unsent ones in the same chat (order kept). After 24 h of failures the item becomes **Not sent · Retry** (receipts are dropped silently instead). Errors that can't succeed on retry (`not_verified`, `forbidden`, `validation`, `safe_mode_blocked`) fail at once with their message.
- R-07.18 Idempotent send: each item has a `client_id` (the payload `id`, 96 random bits). The item is MLS-sealed once; retries resend the **same** ciphertext and `client_id`, never re-encrypt. Server keeps `(sender device, client_id) → result` for 7 d and answers a repeat with the first result, storing and pushing nothing again. Result: no duplicates even when the response was lost. Recipients additionally dedup by payload `id`.
- R-07.19 Timeouts and network state: send request timeout 15 s, other chat calls 10 s; a timeout counts as "unknown" and is retried (safe under R-07.18). Network state = the realtime connection to our server (what matters for delivery; no extra native module): down for ≥ 3 s → chat header chip "Waiting for network", composer stays usable, Sending items stay Sending (no red error for being offline).
- R-07.20 Receive integrity: messages are processed in server order (`id`) per device; a batch is acked only after its results are committed to the local store in one transaction, so a kill mid-batch re-delivers instead of losing. A message that can't be decrypted is **not** dropped: it is kept (up to 24 h, re-tried after each new welcome/commit, since it may have arrived before them), then shown as a "Message couldn't be decrypted" row. In a 1:1 chat the device then re-syncs: it forgets the broken group, starts a new one (welcome to every peer device) and sends `{t: 'resync', drop: <old group id>}` in it, so the peer forgets the old group too. Server message ids already handled are remembered (last 2,000), so a re-delivery after a kill is acked without being processed twice. MLS state keeps the previous 3 epochs so late messages after a commit still decrypt. **Stale device (#206)**: when a send to a 1:1 group is refused with 422 `to_device_id: unknown device` (the other person reinstalled, signed out or removed a device), the sender drops that group once, starts a new one with the peer's current key packages and sends the same message again (new seal, same id); queued messages sealed into the dropped group are sealed again. Only a second refusal shows "Not sent". In the thread, messages sort by sender time clamped to [server time − 5 min, server time] (stops a wrong phone clock reordering the chat), then by arrival.
- R-07.21 Local store: one encrypted row per message (no per-chat JSON blob, no 500-message cap). Only the disappearing timer (R-07.6), view-once, "Delete for me" and chat delete remove messages. All writes to one conversation are serialized, so a send and a receive at the same moment can't overwrite each other.
- R-07.22 Server write is atomic: all envelopes of one `POST /mls/messages` are stored, or none (validation / limits fail the whole call). Undelivered ciphertext stays queued 30 d (R-07.12); a device offline longer gets a "Some messages expired while you were away" row per affected chat (count only, from the server's swept-count per device).
- R-07.23 Read receipts (Settings › Privacy › Read receipts, default on; covers Delivered, Read and typing): off → the device sends no `delivered`/`read`/typing **and** ignores incoming ones (enforced on the client for receipts, on the server for typing). Per-chat override in chat ⋯ › "Read receipts in this chat: Default / Off" (Off is symmetrical in that chat too). Receipts travel only inside MLS (server never learns who read what); in group chats Read shows a count, never names.
- R-07.24 Timing: online recipient p95 < 500 ms send → Delivered intra-EU (AC-07.2). Offline recipient: content-free push at once (throttle 1 per account per 20 s, F-16); messages wait server-side until a device pulls. Server measures insert → ack latency per message as an aggregate histogram only (no ids, no pairs).

## Translation (#106, on device only)
Goal: two people with no shared language can still chat. Privacy first: translation never breaks E2EE.
- R-07.25 Where: incoming `text` messages (and custom quick replies, group chats included) are translated **on the reader's phone**: iOS 18+ Apple Translation framework (`TranslationSession`) with NaturalLanguage `NLLanguageRecognizer` for detection; Android (#107, same module `modules/thirstr-translate`, Kotlin): Google ML Kit Language ID (`com.google.mlkit:language-id`, model bundled in the app) for detection and ML Kit Translation (`com.google.mlkit:translate`, ~30 MB model per language, pairs pivot through English) for translation. Language ID tags are reduced to the base language; romanized guesses (`hi-Latn`) count as unsure; legacy codes map to ML Kit's (`iw`→`he`, `in`→`id`, `ji`→`yi`, `fil`→`tl`). Any Android version the app supports. Plaintext never goes to Thirstr or any translation service. Only language packs are downloaded, from Apple or Google, and they carry no message content. No cloud fallback in beta (D-16).
- R-07.26 Target language = the phone's first preferred language (`getLocales()[0].languageCode`, can differ from the app's en/fr/de). Source = detected per message: at least 8 letters, confidence ≥ 0.6, otherwise not translated (short words like "ok", emoji-only, links). Same language as target → nothing shown. Own messages are never translated: the sender always sends what they typed (no `lang` field on the wire, nothing new in the payload).
- R-07.27 Setting (device-only, Settings › Chats & media › Translation): **Translate messages** Automatic (default) / Tap / Off. Automatic: translated as the bubble appears when the language pack is on the phone. Tap: a "Translate" chip under the bubble. Off: nothing. Per-chat switch in chat ⋯ "Translate this chat" (on by default; off = nothing in that chat, stored on the device in `Conv.translate`; hidden when the device can't translate or the global setting is Off).
- R-07.28 Bubble: shows the translation; caption under it "Translated from ‹language› · Show original" (translate icon in teal). Show original expands the bubble: translation, hairline, original in secondary colour, caption "‹language› · Hide original". Copy / long-press use what is shown. At the top of a chat with a translated message, a teal note under the E2EE pill: "‹Source› is translated to ‹target› on this phone. Nothing leaves it."
- R-07.29 Language pack missing (status `supported`, not `installed`; Android: source or target model not downloaded): even in Automatic, nothing is downloaded silently; the bubble shows the original plus chip "Translate ‹language›" and caption "One-time download of the language pack. Your messages stay on this phone." Tapping it shows the system download sheet (iOS) or downloads the missing model(s) at once on any network with the chip reading “Translating…” (Android; the tap is the consent, the caption announces it), then translates. Unsupported pair, device below iOS 18, web, or error → original only, no chip.
- R-07.30 Storage: translations are cached in the encrypted device store (`tr:<conv>␁<message id>` = `{from, to, text}`), deleted with the message (disappearing timer, delete for me, delete chat, R-07.21). Never synced, never in exports to other people, never in reports: a report sends the original plaintext only (R-07.11).
- R-07.31 Quick replies: the 6 built-in quick replies (R-07.5) carry their index `k` in the E2EE payload (`{t: 'quick_reply', text, k}`); the reader shows the built-in text in their own app language. `text` stays as the fallback for older apps. Custom quick replies are translated like text.

## Favorites, notes and friends (#115, layout A)
Goal: keep track of the people who matter without anyone else knowing. [Mockup](https://claude.ai/artifact/333MUDiSEuQkEYKCM3RmDA) (option A chosen). All three are **device-only** (encrypted store); none is sent to the server. Sync across own devices comes with device linking (B4, same as R-06.9).
- R-07.32 **Favorite** = private star on a person (profile id), not on a chat. Stored `fav:<profile id>` = time added. The other person never knows. Set or clear from: chat header star button (44 pt round; on = `personal` fill + ink star), chat ⋯ "Add to favorites / Remove from favorites", inbox long-press menu, profile S-20 star button (R-06.10). Group chats have no favorite; their long-press "Pin" keeps them on top (old `Conv.starred` on a group). Migration: a 1:1 chat with `starred` becomes a favorite of its peer once, then `starred` is cleared.
- R-07.33 **Inbox (S-40)**: search field under the title, then segmented **All · Unread · Favorites · Friends** (selected = `mode.hookup` for All/Unread, `personal` for Favorites, `mode.friends` for Friends). The old "New" segment goes; "New" stays as a section inside All (R-07.8). All: a **favorites strip** at the top when there is ≥ 1 favorite (horizontal, 62 pt avatars with 2.5 pt `personal` ring, online dot, first name 12 pt; most recent activity first; tap → chat if one exists, else profile S-20). Rows show a sunflower star after the name for favorites and a violet "Friend" badge for friends. Favorites tab: favorites with a chat (by last activity), then favorites without one ("Say hi" row → profile). Friends tab: section **Friend requests** on top when any are incoming (each row: photo, "‹name› wants to be friends", round × = Not now, violet Accept), then sections **Online** and **Friends** (by name). Online = `online` from `GET /profiles/:id` (same symmetric rule as Explore, R-17.5), refreshed when the tab opens. Empty tabs: "No favorites yet. Tap the star on someone you like." / "No friends yet. Add a friend from a chat."
- R-07.34 **Search** filters, on the device only: display name, last message preview, private note text and tags. Matching note text shows as the third row line. Clearing search restores the tab.
- R-07.35 **Private note in chat (S-41)**: when a note or tags exist for the peer (R-06.9, key `note:<profile id>`), a strip under the header: 1.5 pt dashed `personal` border, radius 18, pen icon, note text (2 lines max), tag chips (`personal` fill, ink 12/800), label "Only you" right. Tap → note sheet: text field (500 chars, `personal` focus border), tag chips (max 10; existing own tags offered as suggestions, + Tag adds one), "Kept on this phone" caption, sunflower Save. No note → chat ⋯ "Add private note" opens the same sheet. Inbox rows show a sunflower pen + note (first tags, else text) as a third line.
- R-07.36 **Friends** are mutual. Offered in chat ⋯ and profile ⋯ once a 1:1 chat exists (any message either way) and the sender is verified (R-07.2). Messages travel as E2EE payloads in the 1:1 MLS group, so **the server never learns who is friends with whom**: `{t: 'friend', op: 'request' | 'accept' | 'decline' | 'cancel' | 'remove'}`. State per peer `friend:<profile id>` = `out` (pending, sent) · `in` (received) · `yes`. No state = not friends.
  - Request: sender sees a violet card in the chat "You asked ‹name› to be friends · Pending"; receiver sees a card "‹name› wants to be friends" with **Accept** (violet) / **Not now**, plus the Friends tab request row. Not now sends `decline`; the sender's state simply returns to none (no "declined" shown; they may ask again after 7 days, enforced on the sender's device).
  - Accept → both `yes`; system line in the chat "You and ‹name› are friends" (violet check).
  - Remove (chat ⋯ / profile ⋯ "Remove friend") sends `remove`: both sides drop it quietly, no message shown to the other side.
  - Both sides request at once → treated as accept.
  - Block, report-and-block, or the profile going away → friend state deleted locally, nothing sent.
- R-07.37 **Tap vs favorite**: Tap (F-06) gets its own flame icon (coral when sent) on S-20 and in the inbox Taps row, so the star means favorite everywhere.
- R-07.38 Privacy: favorites, notes and friends are in "Download my data" (device part), never in reports (R-07.11), never on the server. Deleting a chat keeps favorite and note (they belong to the person); it keeps friend state too.
- R-07.43 Explore can show only favorites or friends (F-04 R-04.22, #247); the lists stay on the phone, the filter runs there.
- R-07.44 **Friend perks** (#247, [mockup board "What friends get"](https://claude.ai/artifact/333MUDiSEuQkEYKCM3RmDA)). Friends (R-07.34) unlock the rules below. Each one is resolved on the phone and travels only inside the 1:1 E2EE chat; the server never learns who is friends with whom. Ending a friendship (remove, block, report) takes every perk back at once.
  - Moments: audience **Friends** (F-21 R-21.29).
- R-07.45 Private album **Open to all friends** (F-08 R-08.18): switch on the album screen. On → an `album.grant` to each accepted friend's chat (sub line "N friends can open it, new friends too"); a new friend gets it on accept; a share made this way shows "Friend · open to all friends". Off, unfriend or block → `album.revoke` + item rotation (AC-08.2) for those shares only; shares made by hand stay.
- R-07.46 **Make safety contact** (F-13 R-13.22): chat ⋯ for a friend. Creates the usual trusted-contact invite (R-13.2) and sends its link as `{t:'safety.invite', url}`. The friend sees a teal card "Marco wants you as a safety contact" + why + **Open** (opens only links to our own `/c/#…` page). The sender sees a quiet row "You asked Marco…".
- R-07.47 **Show me to friends** (F-05 R-05.17): Location sheet (S-30) → 1 h / 6 h / 24 h, any level (made for Hidden). While on and while Thirstr is open: the spot rounded to 3 decimals (≈ 100 m) goes as a silent `{t:'friend.loc', lat, lng, until}` to every friend at start, every 10 min and after 200 m; Stop (or expiry) sends `{stop:true}`. Received spots are kept only from friends, capped at 24 h, drawn on Explore like Area people (and in the Friends filter, R-04.22) until `until` or 30 min without an update. Never a chat row, never a push. No background location.
- R-07.48 **Tell me when online** (F-16 R-16.11): chat ⋯ for a friend, max 20. While Thirstr is open (every 10 min and on return to the foreground) the phone reads `online` from `GET /profiles/:id` and shows a local notification "Marco is online" on offline → online, at most once per friend per 2 h. Nothing new is stored on the server.
- R-07.49 **Invite friends** to a party (F-10 R-10.12): host's party screen → sheet of friends (all ticked, Select all) → `{t:'party.invite', party, code?, title, starts_at}` in each 1:1 chat. Card: "Marco invites you" + title + time + **See party** (opens S-14 with the code for invite-only parties).
- R-07.39 **Search in a chat** (#121, [mockup](https://claude.ai/artifact/333MUDiSEuQkEYKCM3RmDA#artboard-Search)): chat ⋯ › "Search in chat". The header becomes a search field (2 pt `personal` border, autofocus) + Done; the composer becomes a bar with "N of M" (or "Type at least 2 letters" / "No matches"), a teal lock line "Searched on this phone only" and up (older) / down (newer) 44 pt buttons. Runs only on the device over the local store: text, quick replies (built-in ones in the app language), album names; case- and accent-insensitive, from 2 letters. Matches show the term marked in `personal` (ink text); non-matches dim to 35 %; the current match has a 2 pt `personal` ring and is scrolled to the middle; newest match first; Return goes to the next one. Translated bubbles match on the original text. No search for people by name anywhere in the app (stalking risk); people you know are found through Chats search (R-07.34).
- R-07.40 **Chats Spotlight** (S-40, #211, [mockup A](https://claude.ai/artifact/RzKMnX67pWujoMPQDnRoD2#artboard-Main)): the Taps entry is a **full-width coral button** (min 72 pt, radius 24, coral glow) above the tabs, on every tab while the search is empty: up to 2 faces of the latest unseen tappers (44 pt, 3 pt coral border, 16 pt overlap), then an ink flame disc with a pulsing ring and a 3 pt bob (UI thread; stops while Chats is not focused, with no new Taps, and with Reduce Motion), title "N new Taps" (else "Taps"), line "Marco, Leo and 1 more · 1 mutual" (else "See who tapped you"), ink chevron disc. Opens the Taps list. The E2EE notice moves to a teal chip "End-to-end" right of the title; the list footer only explains Favorites / Friends.
- R-07.41 **Live typing in the list**: a 1:1 row whose peer is typing (R-07.23 receipts on) shows "typing" + three breathing dots instead of the preview (coral when unread, else violet); ends 6 s after the last event.
- R-07.42 **Rings by state**: chat avatars (56 pt) get a 2.5 pt ring: coral = unread, violet = friend, none otherwise; the favorites strip uses the same, sunflower otherwise. Unread rows show their time in coral. Tabs are equal-height segments, selected = white; Unread carries a coral count badge (chats with unread, not archived; 99+). Section "New" is renamed **Your move** (they wrote, you have not yet).

## Edge cases
- Recipient blocks sender mid-chat → sender sees "Message not delivered" without revealing block (generic).
- Recipient deleted account → chat archived "This profile is gone".
- Key package exhausted → client uploads 100 on each launch; fallback last-resort package.

## Acceptance criteria
- AC-07.1 Server DB/logs contain no plaintext message content in any env.
- AC-07.2 p95 delivery online < 500 ms intra-EU.
- AC-07.3 First message containing URL from new contact is blocked client-side and rejected (flag) server-side by franking-based heuristics on report only (no server scanning).
- AC-07.4 Disappearing timer deletes on both devices within 1 min of expiry.
- AC-07.5 Airplane mode: write 5 messages, kill the app, relaunch, restore network → all 5 arrive exactly once, in order, without user action.
- AC-07.6 Proxy drops the response to `POST /mls/messages` → client retries; recipient shows exactly one copy.
- AC-07.7 Recipient app killed mid-batch → after relaunch no message missing, none duplicated.
- AC-07.8 Receipts off (global or per chat) → no `delivered`/`read`/typing sent; incoming ones not shown.
- AC-07.9 A chat with 2,000 messages keeps all 2,000 (until timer/user delete).
- AC-07.10 Message arriving before its welcome/commit decrypts once they arrive; never silently disappears.
- AC-07.11 German phone receives "Are you still around tonight?" with the English pack installed → bubble shows the German translation and "Translated from English · Show original"; a network capture shows no request carrying the text.
- AC-07.12 Translate messages Off (global) or chat switch off → no translation, no chip. Tap → chip only. Pack missing → chip with download note, no silent download.
- AC-07.13 Quick reply "Yes 🔥" sent from an English app shows "Ja 🔥" on a German app.
- AC-07.14 Deleting a message (any way) deletes its cached translation.
- AC-07.15 Starring Marco in his chat shows him in the favorites strip and the Favorites tab; the server database and logs have no trace of it.
- AC-07.16 A note "met at Bear night" with tag gym shows under Marco's chat header and on his inbox row; searching "gym" in Chats finds his chat.
- AC-07.17 A sends a friend request, B accepts → both see each other in Friends with a "Friend" badge; server stores only ciphertext (no friend table, no new endpoint). B taps Not now → A's card goes back to "Add as friend" with no "declined" text.
- AC-07.18 Remove friend on one side removes it on both within one delivery; block removes it on the blocker's side without sending anything.
- AC-07.19 In a chat with three messages mentioning Langstrasse, searching "langstr" shows "1 of 3" on the newest, up moves to "2 of 3" and scrolls to it; a network capture shows no request carrying the term.
